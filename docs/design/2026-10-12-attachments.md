# File attachments — design

Date: 2026-10-12 · Status: draft for review · Target: 1.6.0

End-to-end-encrypted files on records, like Keeper's attachments: a file is encrypted in the browser under its own
key, that key is wrapped under the record key, and the server stores and serves ciphertext only. Anyone who can open
the record can open its files; nobody else, the server included.

Related: `2026-10-04-clane-vault-design.md` (§5 crypto model), `2026-10-08-per-org-keypairs.md`, `docs/sharing.md`,
`docs/policies.md`, `docs/install-app.md` (offline copy), `docs/migrate-from-keeper.md`, `docs/risk-dashboard.md`.
Assumes RecordBody v2 (record types and custom fields, `packages/crypto/src/recordTypes.ts`) has landed: attachments
are independent of the record type and work on every type.

## 1. Goals and non-goals

**Goals**

- Attach files to any record (every `RecordType`, private or in a team folder, owned or shared): add, list, download,
  preview, remove.
- Zero knowledge, same as records: the server never sees a file's name, type or content; it stores ciphertext and
  learns sizes, counts and timestamps (§2.6).
- Access follows the record: sharing a record (direct share, team folder) shares its files with no re-encryption;
  removing access stops the server serving the ciphertext at once (§4.5).
- Works unchanged behind today's proxies: every request body stays under the API's 2 MB `bodyLimit` and the 5 MB the
  install guide asks proxies for (`deploy/client/README.md`), so uploads are chunked (§4).
- Keeps the one-container story: files live in Postgres by default, so `pg_dump` backups and restores keep covering
  everything; S3-compatible object storage is an option by env for large deployments (§3).
- Previews in the browser after decryption for images and PDFs; everything else is download-only.
- Resumable uploads (within a session), progress, cancel, retry; quotas per organisation, per person and per instance.

**Limits (defaults, overridable by env, §3.4)**

| Limit | Default | Why |
|---|---|---|
| File size | 100 MiB | Keeper's own limit is 100 MB on business plans; one file fits in memory on a phone for download. |
| Files per record | 25 | Keeps the panel usable and the sync response small. |
| Per-record total | 250 MiB | Bounds the cost of one record for links and quota. |
| Per-organisation quota | 2 GiB | Fits a bundled-Postgres install on a small VPS, with backups. |
| Per-person quota (private records) | 512 MiB | Private files count against the owner, not an org. |
| Per-instance quota | 10 GiB | The operator's ceiling over every org and person; managed Postgres plans need it set lower (§3.3). |
| Uploads per person per day | 2 GiB | Abuse brake. |

**Non-goals (this release)**

- No server-side scanning for malware. The server holds ciphertext, so it can't scan. The client never renders an
  attachment as HTML, SVG or any scriptable document, serves downloads as `application/octet-stream` with
  `content-disposition: attachment`, and previews only an allowlist of formats through safe sinks (§6.4, §7.5).
  The event log records who added each file (§5.5), and the panel shows that name next to every file.
- No attachment history or versions. A file is immutable; replacing it is remove + add.
- No per-attachment trash. Removing a file deletes it at once (the record's trash covers the whole record, §3.6).
- No hiding of file sizes (the server learns ciphertext size, which is plaintext size plus 16 bytes per chunk).
- No attachments in the browser extension (read-only listing at most, §5.3), none in the offline copy (§5.2).
- No pre-signed S3 URLs handed to browsers (the API proxies every byte so authorization stays in one place, §3.2).
- No folder-level attachments, no attachments on one-time links by default (opt-in per link, §5.1).

## 2. Crypto

All of this lives in `packages/crypto/src/attachments.ts`, exported from `index.ts`, with known-answer and negative
tests in `packages/crypto/test/attachments.test.ts`. It reuses `aeadEncrypt`/`aeadDecrypt` (`v1.` envelopes with AAD)
for the small values, and raw AES-256-GCM through Web Crypto for the chunks (no base64: chunks travel as bytes).

### 2.1 Keys

```
recordKey (32 B, per record, unchanged)
   │ AES-GCM v1., AAD attachment-key:<recordId>:<fileId>          → Attachment.wrappedFileKey
   ├──► fileKey (32 B, random per file, never reused)
   │        │ AES-GCM raw, nonce = nonceBase ‖ BE32(index), AAD attachment-chunk:<fileId>:<index>:<chunkCount>
   │        └──► chunk ciphertexts (AttachmentChunk.data, or S3 objects)
   │ AES-GCM v1., AAD attachment-meta:<recordId>:<fileId>         → Attachment.encMeta
   └──► {name, mime, size, sha256, chunkSize, chunkCount}
```

- **`fileKey`**: `randomBytes(32)`, generated by the uploading client, used for one file's chunks only. It is wrapped
  under the record key exactly like a record key is wrapped under a holder key (`wrapKey(fileKey, recordKey,
  "attachment-key:<recordId>:<fileId>")`). The AAD binds the wrap to one record and one file id: the server can't move
  a wrapped file key to another record or another attachment row.
- **Metadata** is encrypted under the **record key** (not the file key) with `aeadEncrypt`'s random IV, so the file
  key is only ever used with the structured chunk nonces below and there is no nonce-space overlap to reason about.
  Metadata is `{ name, mime, size, sha256, chunkSize, chunkCount }` as JSON (≤ 2 KiB; the name is cut at 255
  characters; `sha256` is the hex digest of the plaintext, `size` its byte length).
- Why not in the record body: the body is capped at ~49 KB of JSON and every change bumps the record revision; an
  attachment add or remove must not conflict with a concurrent field edit, and the body must stay small for the
  extension and the offline copy. Attachment rows are separate (§6.2), and the record body does not reference them.

### 2.2 Chunks

- `chunkSize` = 1 MiB (1 048 576 bytes) of plaintext. Every chunk but the last is exactly `chunkSize`; the last is
  1..`chunkSize` bytes (a zero-byte file has one empty chunk, so `chunkCount ≥ 1`). Ciphertext of a chunk is
  plaintext + 16-byte tag; it fits in the 2 MB body limit with room to spare, and no proxy needs changing. 4 MiB
  chunks would halve the request count but would need a 5 MB body limit and a proxy change; 1 MiB is also a better
  resume and progress granularity. 100 MiB = 100 requests.
- `chunkCount = max(1, ceil(size / chunkSize))`, known before the first chunk is sent (the client has the `File`).
- **Nonce** (12 bytes) = `nonceBase` (8 random bytes, generated with the file key, stored in clear in
  `Attachment.nonceBase`) ‖ big-endian 32-bit chunk index. Unique per chunk because the key is unique per file and the
  index is unique per chunk. The random base is defence in depth against a bug that reuses a key.
- **AAD** = `attachment-chunk:<fileId>:<index>:<chunkCount>` (UTF-8). It binds every chunk to its file, its position
  and the total count, so the server (or anyone with database access) can't:
  - **reorder** chunks (index in AAD);
  - **truncate** the file (every chunk carries the total, and the client requires exactly `chunkCount` chunks and
    checks the last chunk's plaintext length makes `size`);
  - **swap** a chunk in from another file (file id in AAD, and a different key anyway);
  - **replay** an older chunk: chunks are immutable once accepted (§4.2), so there is no older version to replay.
- **Whole-file check**: after decrypting all chunks the client compares the streaming SHA-256 of the plaintext
  (`hash-wasm`'s incremental `createSHA256`, already a dependency) with `meta.sha256`. This catches a client-side bug
  as well as any mix-up the per-chunk checks might miss; a mismatch is shown as "File is damaged, ask the person who
  added it to upload it again" and the download is discarded.
- **Never encrypt the same chunk twice.** A GCM nonce must never be reused with different plaintext. The client
  encrypts each chunk once, keeps that ciphertext in memory until the server has confirmed it, and retries with the
  same bytes. A resume after a page reload (where the ciphertext is gone) starts over with a **new** file id and a
  **new** file key; it never re-encrypts under the old key, because the file on disk may have changed meanwhile. The
  server enforces the same thing: a chunk index that already exists is accepted again only if the bytes are
  identical (§4.2).

### 2.3 Functions

```ts
// packages/crypto/src/attachments.ts
export interface AttachmentMeta { name: string; mime: string; size: number; sha256: string; chunkSize: number; chunkCount: number }
export const ATTACHMENT_CHUNK_SIZE = 1_048_576;
export const MAX_ATTACHMENT_BYTES = 100 * 1024 * 1024;           // the crypto package's ceiling; the server's limit may be lower

export function newAttachment(size: number): { fileKey: Uint8Array; nonceBase: Uint8Array; chunkCount: number };
export function wrapFileKey(recordId: string, fileId: string, fileKey: Uint8Array, recordKey: Uint8Array): Promise<string>;      // v1.
export function unwrapFileKey(recordId: string, fileId: string, wrapped: string, recordKey: Uint8Array): Promise<Uint8Array>;
export function encryptAttachmentMeta(recordId: string, fileId: string, meta: AttachmentMeta, recordKey: Uint8Array): Promise<string>;
export function decryptAttachmentMeta(recordId: string, fileId: string, encMeta: string, recordKey: Uint8Array): Promise<AttachmentMeta>; // validates shape and limits
export function encryptChunk(fileKey: Uint8Array, nonceBase: Uint8Array, fileId: string, index: number, chunkCount: number, plaintext: Uint8Array): Promise<Uint8Array>;
export function decryptChunk(fileKey: Uint8Array, nonceBase: Uint8Array, fileId: string, index: number, chunkCount: number, ciphertext: Uint8Array): Promise<Uint8Array>;
export function chunkPlan(size: number): { chunkCount: number; lastChunkBytes: number };
/** Safe filename for the download: control characters, path separators and leading dots stripped; "file" when empty. */
export function safeFilename(name: string): string;
```

`decryptAttachmentMeta` rejects metadata whose `size`, `chunkSize` or `chunkCount` disagree with `chunkPlan`, whose
`mime` is not `type/subtype` ASCII, or whose name is empty after `safeFilename`: a bad row shows as "Can't open this
file" and nothing is downloaded.

### 2.4 One-time links (§5.1)

A link snapshot that includes files carries, under the link key, `attachments: [{ fileId, fileKey (b64url),
nonceBase, meta }]`. The recipient decrypts chunks with the real file key. Nothing is re-encrypted; what a link
exposes is the file key itself, which is why files are opt-in per link and logged.

### 2.5 Nothing else changes

Record keys, folder keys, membership keys, sealing, rotation and recovery are untouched. Rotating a folder key
re-wraps record keys only; file keys hang off the record key and need no work. A scoped admin recovery that restores
a membership key restores files with it, because files come with the record key.

### 2.6 What the server learns

| Known to the server | Not known |
|---|---|
| that a record has N attachments, each one's id, ciphertext size (plaintext + 16 B × chunks, so the size to within a few bytes), chunk count, who added it and when | file name, type, content, SHA-256 of the content |
| who downloaded which file when (event log; chunk 0 requests) | whether two attachments are the same file (different keys and nonces: identical files give unrelated ciphertext) |
| per-org, per-person and per-instance usage in bytes | anything about the record body |

## 3. Storage

### 3.1 Options

| Option | For | Against |
|---|---|---|
| **Postgres, one row per chunk (`bytea`)** | One container, one backup (`pg_dump` already covers it), one restore drill, transactional with the metadata (no orphan objects), works on every managed Postgres, no new credentials. | Database grows by the attachment volume; dumps and restores take proportionally longer; managed plans price database GB far above object-storage GB. |
| Local volume in the container | Fast, cheap. | Breaks the stateless single-container story (a second volume to mount, back up and restore separately); no managed-Postgres deployment can use it; orphan and consistency handling to write. |
| S3-compatible object storage | Cheap per GB, scales, already configured for backups (`BACKUP_S3_*`), Supabase Storage speaks S3. | A second system to keep consistent (orphans, GC), backups must cover the bucket separately (versioning or replication), extra latency per chunk, credentials with write access on the API. |

**Recommendation.** Postgres by default (`ATTACHMENT_STORAGE=db`), S3 by env for large deployments
(`ATTACHMENT_STORAGE=s3`). The defaults above (2 GiB per org, 10 GiB per instance) are sized for the database
option; an operator who raises them should move to S3. Both backends share the same `Attachment` metadata rows and the
same API; only where chunk bytes live differs, behind one interface:

```ts
// apps/api/src/lib/attachments/store.ts
interface ChunkStore {
  put(attachmentId: string, index: number, data: Uint8Array): Promise<void>;     // idempotent for identical bytes
  get(attachmentId: string, index: number): Promise<Uint8Array | null>;
  has(attachmentId: string): Promise<Set<number>>;                                // received indices (resume)
  deleteAll(attachmentId: string): Promise<void>;
}
```

- `DbChunkStore`: table `AttachmentChunk` (§6.2). The migration sets `ALTER TABLE "AttachmentChunk" ALTER COLUMN
  "data" SET STORAGE EXTERNAL` so Postgres doesn't waste CPU trying to compress incompressible ciphertext into TOAST.
  Reads and writes use `$queryRaw`/`$executeRaw` with `Buffer` parameters rather than Prisma's `Bytes` through the
  JSON protocol (which base64-encodes every chunk, 1.33× overhead).
- `S3ChunkStore`: objects at `<ATTACHMENT_S3_PREFIX><attachmentId>/<index>` with `Content-MD5`, reusing
  `lib/backup/destinations.ts`'s client; `has` lists the prefix. The API streams objects to the browser; no pre-signed
  URLs (§1).
- Switching backends later: a `node dist/src/scripts/attachments-move.js --to s3` script copies chunks and flips
  `Attachment.storage` per row (each row says where its chunks are, so a half-migrated instance keeps working).

### 3.2 Serving

Chunk downloads go through the API in every case (authorization, event logging and the `use`-only rule live there),
as `application/octet-stream` with `cache-control: no-store` (already the API default), `content-disposition:
attachment; filename="<fileId>.<index>.bin"` and `x-content-type-options: nosniff` (already set). Memory per
request is one chunk.

### 3.3 Effect on backups and managed Postgres

- **Dump size.** `pg_dump --format=custom` writes `bytea` hex-escaped (2 bytes per byte) and then compresses with
  zlib level 6 by default. On ciphertext the hex doubling is undone by compression but level 6 is slow (~20–40 MB/s of
  input on one core). The backup moves to `--compress=1` (`lib/backup/service.ts`): about the same final size (~1.1×
  the raw ciphertext) at roughly 3× the speed. Rule of thumb: an instance with 5 GiB of attachments produces a ~5.5 GB
  encrypted dump and the run takes a few minutes instead of seconds. `RUN_TIMEOUT_MS` (6 h) stays. The Backups page
  shows the attachment share of the last dump (`Attachment.size` sum at run time, recorded in `BackupRun`).
- **Restore.** `pg_restore` of the same dump; nothing new. The restore drill in `docs/operations.md` gets a line on
  expected duration per GB.
- **Excluding chunks from the dump.** With `ATTACHMENT_STORAGE=s3` the dump excludes `AttachmentChunk` data
  (`--exclude-table-data`), and the install guide says that the bucket must be backed up by the operator (object
  versioning or cross-bucket replication). With `db` storage nothing is excluded: one dump restores everything.
- **Supabase and other managed Postgres.** Database storage is the expensive part of those plans (Supabase: 500 MB on
  Free, 8 GB included on Pro, then per GB-month; egress is also metered and every download leaves through the API, not
  through the database). Guidance in the install guide: on Free, set `ATTACHMENT_INSTANCE_QUOTA_MB=200` or turn
  attachments off; on Pro with real use, set `ATTACHMENT_STORAGE=s3` with Supabase Storage's S3 endpoint (the same
  settings already documented for backups). Transaction-mode poolers are already discouraged; chunk writes are single
  statements and work either way.
- **Startup check.** With `db` storage the server logs a warning at start and shows an instance-admin banner when
  attachment usage passes 80 % of `ATTACHMENT_INSTANCE_QUOTA_MB`, and the Risk dashboard's backups benchmark notes the
  dump size.

### 3.4 Configuration (`config.ts`)

| Env | Default | Meaning |
|---|---|---|
| `ATTACHMENTS_ENABLED` | `true` | Off: every attachment route answers `404 attachments_disabled`, the UI hides the feature. |
| `ATTACHMENT_STORAGE` | `db` | `db` or `s3`. |
| `ATTACHMENT_S3_ENDPOINT`, `_REGION`, `_BUCKET`, `_PREFIX` (default `attachments/`), `_ACCESS_KEY_ID`, `_SECRET_ACCESS_KEY`, `_FORCE_PATH_STYLE` | — | Required with `s3`. Separate from `BACKUP_S3_*` on purpose (different bucket, write-only backup credentials). |
| `ATTACHMENT_MAX_FILE_MB` | `100` | Hard per-file ceiling (1–1024). Orgs may lower it by policy, never raise it. |
| `ATTACHMENT_MAX_PER_RECORD` | `25` | |
| `ATTACHMENT_MAX_RECORD_MB` | `250` | |
| `ATTACHMENT_ORG_QUOTA_MB` | `2048` | Per organisation (team-folder records and records shared in it count for the org that holds them, §3.5). |
| `ATTACHMENT_USER_QUOTA_MB` | `512` | Per person, for their private records. |
| `ATTACHMENT_INSTANCE_QUOTA_MB` | `10240` | Everything together. |
| `ATTACHMENT_DAILY_UPLOAD_MB` | `2048` | Per person per rolling 24 h, counted at create. |

Org policy additions (`docs/policies.md`, `lib/policies.ts`): `attachments.allowed` (default on),
`attachments.maxFileMb` (null = instance max; may only lower it), `attachments.previews` (default on; off makes every
file download-only), `links.allowAttachments` (default on; off: links can't carry files). Changing
`attachments.allowed` to off doesn't delete anything: existing files stay listed and downloadable, no new uploads
(`403 attachments_disabled`); the setting page says so.

### 3.5 Quotas and accounting

- An attachment is **charged to** the record's organisation (`recordOrgOf`: the team folder's org) or, for a private
  record, to its owner. A direct share in an org of a private record doesn't move the charge: the owner still pays.
- Usage is a `SUM(size)` over `Attachment` rows in state `uploading` or `ready` (uploading rows reserve their declared
  size), computed with the indexes in §6.2. At a few thousand files this is milliseconds; a cached counter isn't
  needed yet.
- The reservation happens at create (§4.1) inside a transaction that takes `SELECT … FOR UPDATE` on the
  `Organization` row (or the `User` row for private records), like the link policy check, so two concurrent uploads
  can't both squeeze under the limit. Instance usage is checked in the same transaction with an advisory lock
  (`pg_advisory_xact_lock(7342)`).
- Moving a record into a team folder (`PUT /records/:id/folder`) re-charges its attachments to that org: the move
  is refused with `409 quota_exceeded` if the org's quota can't take them. Moving to private re-charges the owner.
  Offboarding that hands records to the folder owner changes nothing (same org).
- Refusals: `413 file_too_large { max }`, `409 quota_exceeded { scope: "org" | "user" | "instance", used, quota }`,
  `409 too_many_files`, `409 record_too_large`, `429 daily_upload_limit`.

### 3.6 Garbage collection

| Event | What happens |
|---|---|
| Remove one file (`DELETE …/attachments/:fid`) | The row goes to state `deleted` in the same transaction as the event; chunks are deleted right after the response (db: `DELETE FROM "AttachmentChunk"`; s3: objects), then the row. Usage drops when the row leaves `ready`. |
| Record trashed | Nothing is deleted. Attachments stay listed; downloads and uploads are refused (`409 in_trash`). Restore brings everything back. Quota stays charged (the data is still there). |
| Record purged | `Attachment` rows cascade with the record (FK); their chunks are removed by the sweep (db: rows cascade with `Attachment`; s3: objects listed from `AttachmentTombstone`, written in the purge transaction). |
| Account deleted | Records cascade today; same path. |
| Upload abandoned | `uploading` rows older than 24 h are swept: chunks deleted, row deleted, reservation released. The client also sends `DELETE` on cancel. |
| Org deleted | Records in its folders go as today; chunk cleanup follows. |

The existing sweep interval in `app.ts` (`SWEEP_INTERVAL_MS`) gets `sweepAttachments(prisma, store)`: abandoned uploads,
`deleted` rows whose chunks are still there, and tombstones. The S3 path tolerates partial failure (retry next sweep).
A `GET /admin/instance/storage` report lists orphans found so the operator can see the GC is healthy.

## 4. Upload and download protocol

All routes are under `/api/v1`, authenticated, with `X-Org-Id` optional (`orgOptional`, `privateLockGuard`) exactly
like `routes/records.ts`. Authorization is `accessFor(prisma, userId, recordId, ctx)` in every handler, so a record in
another org's team folder is `404`, and a direct share counts only in the org it was made in.

### 4.1 Create (reserve)

`POST /records/:id/attachments`

```json
{ "id": "<uuid, client-generated>", "encMeta": "v1.…", "wrappedFileKey": "v1.…", "nonceBase": "<b64url 8 B>",
  "size": 10485776, "chunkSize": 1048576, "chunkCount": 10 }
```

- Needs `edit` or `owner`; record not in trash (`409 in_trash`); org policy `attachments.allowed`; `size` is the
  **ciphertext** total and must equal `plaintextSize + 16 × chunkCount` for some plaintext size within
  `chunkPlan` (the server checks `chunkCount = max(1, ceil((size − 16·chunkCount) / chunkSize))` and
  `chunkSize = 1 048 576`); limits and quota (§3.5).
- Creates the row in state `uploading`, logs nothing yet, answers `201 { id, expiresAt }` (`expiresAt` = now + 24 h,
  after which the sweep removes it).
- `409 exists` for a reused id.

### 4.2 Send chunks

`PUT /records/:id/attachments/:fid/chunks/:index` with `content-type: application/octet-stream` and the raw
ciphertext (`chunkSize + 16` bytes, or fewer for the last).

- The route registers its own content-type parser (`parseAs: "buffer"`, `bodyLimit: ATTACHMENT_CHUNK_SIZE + 16`),
  the pattern `routes/brand.ts` uses for logos. JSON bodies are refused (`415`).
- Checks: caller still has `edit` (a share downgraded mid-upload fails here); row is `uploading` and the caller
  created it (`403` otherwise: two people can't fill one upload); `0 ≤ index < chunkCount`; length is exactly
  `chunkSize + 16` unless `index == chunkCount − 1`, where it is `size − (chunkCount − 1) × (chunkSize + 16)`.
- **Idempotent**: the server stores `sha256(chunk)` per index. A chunk for an index already received is `200` when the
  hash matches and `409 chunk_mismatch` when it doesn't (the client then aborts and restarts with a new id, §2.2).
- Chunks may be sent in any order and in parallel (the client uses 3 at a time).
- `200 { received: <count so far> }`.

### 4.3 Resume and complete

- `GET /records/:id/attachments/:fid/upload` → `{ state, received: [indices], expiresAt }`: the client's view after
  a network failure in the same session. (After a reload the client doesn't resume; it `DELETE`s and starts again.)
- `POST /records/:id/attachments/:fid/complete`: in one transaction the server verifies every index `0..chunkCount−1`
  is present and the stored lengths add up to `size`, then sets `state = ready`, `readyAt = now`, and logs
  `attachment.add` (`meta: { size, chunkCount }`). Answers `200 { id, readyAt }` or `409 incomplete { missing: [...] }`.
  The record's `revision` is **not** bumped (attachments aren't in the body), and `Record.updatedAt` is **touched**
  so "modified" sorting and the activity list reflect the change.
- `DELETE /records/:id/attachments/:fid` on an `uploading` row cancels it (creator or record owner).

### 4.4 Download

- `GET /records/:id/attachments` → the list (also present in `/sync`, §6.1): `[{ id, encMeta, wrappedFileKey,
  nonceBase, size, chunkSize, chunkCount, createdBy, createdByName, createdAt }]`, `ready` rows only.
- `GET /records/:id/attachments/:fid/chunks/:index` → the ciphertext bytes (§3.2). Needs `owner`, `edit` or `view`;
  `use` gets `403 use_only` (§4.6); trashed record `409 in_trash`; state must be `ready`.
- Chunk `0` logs `attachment.download` once per (user, file, 10 minutes) to keep the log readable while someone
  retries. Other chunks aren't logged.
- The client fetches 3 chunks in parallel, decrypts each as it arrives, verifies, hashes, and:
  - **download**: with the File System Access API (`showSaveFilePicker`, Chrome and Edge) it streams decrypted chunks
    to disk, so memory stays at a few MiB; elsewhere it collects a `Blob` (≤ 100 MiB by the limit) and triggers
    `<a download>`; the blob's type is **always** `application/octet-stream` (§7.5);
  - **preview**: image or PDF bytes go to the preview sink (§6.4), never to a navigation.

### 4.5 Sharing and revocation

- Nothing changes on share. The file key is wrapped under the record key, and every holder of the record key (owner
  row, folder row, direct share) unwraps it. Adding a folder member, a direct share, completing a pending member,
  re-granting after a reset: all of them hand over the record key, hence the files. No re-encryption, no new uploads.
- Revocation is the record's: removing a share or a folder membership deletes the holder's wrapped record key, and
  from that moment `accessFor` returns null and chunk requests are `404`. Someone who already downloaded keeps the
  file, as with any secret (`docs/sharing.md`, trust limits). Keys aren't rotated on removal (unchanged follow-up).
- The one difference from record bodies: a record body is served to everyone with any permission because it is the
  record. Attachment **chunks are served only on request**, so the server can enforce `view`-or-better and refuse
  `use` (§4.6), and a person removed from a folder can't fetch chunks they hadn't fetched yet.

### 4.6 Permissions

| Action | owner | edit | view | use | none |
|---|---|---|---|---|---|
| See the list (names, sizes, who added) | yes | yes | yes | yes | — |
| Download, preview | yes | yes | yes | **no** (`403 use_only`) | — |
| Add, remove, cancel upload | yes | yes | no | no | — |
| Include a file in a one-time link | yes (Share sheet) | yes (link button) | no | no | — |

`use` is "copy without seeing" (spec §5.6); there is no way to use a file without seeing it, so `use` can't download.
Unlike the password, which the browser must hold to show the record at all, this is enforced by the server
(the ciphertext is never sent), so for files `use only` is a hard limit. The UI shows the file names with a lock icon
and "Ask the owner for Can view to download". (Names are still readable: they are under the record key the holder
already has. That's accepted: the title and username are visible to `use` holders too.)

### 4.7 Rate limits

The global limit is 300 requests per minute per IP (`RATE_LIMIT_PER_MINUTE`). A 100 MiB upload is 102 requests and
a download 100, so the default would throttle two people behind one office NAT. Attachment routes get their own
per-user buckets (keyed by `auth.userId`, `@fastify/rate-limit` `keyGenerator`): chunk uploads and downloads 600 per
minute each, creates 60 per minute, and they are excluded from the global IP bucket. The public link chunk route (§5.1)
is per IP, 300 per minute, separate from the 30 per minute of `/public/links`.

## 5. Everything around it

### 5.1 One-time links

- **Default: files are excluded.** The link sheet lists the record's files with a checkbox each ("Include files",
  all off), a total size, and a warning: "The link carries the keys to these files. Anyone with the link can download
  them until it expires." Org policy `links.allowAttachments` (default on) hides the checkboxes when off. At most
  100 MiB per link.
- `POST /links` gains `attachmentIds: string[]` (optional, ≤ 25). The server checks each is a `ready` attachment of
  that record, stores `ShareLinkAttachment` rows (§6.2), and logs `link.create` with `meta.attachments: n`.
- The snapshot (under the link key, `linkSnapshot`) gets `attachments: [{ fileId, fileKey, nonceBase, meta }]`;
  `LinkBody` and `clean` learn the field (≤ 25, each ≤ 4 KiB; the `MAX_BODY_BYTES` cap moves to 64 KiB for links
  with files, still under the API's 65 536-character envelope).
- `POST /public/links/:id/open` returns, next to `encPayload`, a `downloadToken` (HMAC-signed with `JWT_SECRET`,
  bound to the link id, 30 minutes) when the link has files. `GET /public/links/:id/attachments/:fid/chunks/:index`
  with `authorization: Bearer <downloadToken>` serves the chunk while: the token is valid, the link isn't revoked
  (checked on every chunk: `revokedAt` survives the burn), and the record isn't trashed. The 30 minutes give the
  recipient time to download after the last open burned the payload. Logged once per file as `link.attachment_download`
  (no actor, like `link.open`).
- Revoking the link, revoking the creator's edit right (`revokeLinksOfLostAccess`), trashing the record, or removing
  the attachment all stop the chunks at once. Removing an attachment that a live link includes revokes that link
  (the link would be lying), logged as `link.revoke` with `meta.reason: "attachment_removed"`.
- The public page shows files with sizes and a Download button each (decrypt in the browser as in §4.4), never a
  preview (the public page is unauthenticated and has the least context; download-only keeps the surface minimal).

### 5.2 Offline copy

The sync response includes attachment metadata (ciphertext, small), so the offline vault lists files under a record
with their size and "Available online". Chunks are never stored in IndexedDB: 100 MiB files would multiply the copy
and `saveSync` stores the sync response as received, which has no chunks. No cap logic needed; `docs/install-app.md`
says files need a connection.

### 5.3 Browser extension

No attachments: the popup fills and saves logins. It ignores the `attachments` field of sync (it already ignores
unknown fields). A later item may show a paperclip count in the item view; nothing in this release.

### 5.4 Keeper import

Keeper Commander's `export --format json --zip <file>` writes a zip holding the JSON export and the attachment files
that records reference (the web vault's Settings → Export doesn't include files). **Supported**, in the Migrate from
Keeper page (`docs/migrate-from-keeper.md`), in a later phase (§8, phase 5):

- The page accepts the zip; the 1PUX importer already reads zips in the browser, so the same reader is used. The JSON
  is parsed first (as today), records are created, then each referenced file is read from the zip **entry by entry**
  (`Blob.slice` through the zip reader; never the whole zip in memory) and uploaded with §4 against the new record.
- Guards: an entry whose declared uncompressed size is over the file limit is skipped with a report line; inflating
  stops as soon as the output passes the declared size (zip-bomb guard, §7.6); at most 25 files per record; the org
  quota applies (the plan preview shows "N files, X GB; your organisation has Y GB free" before anything is written).
- The exact JSON field names for file references are confirmed against Commander's `keepercommander/importer/json`
  source and a real export before building; the captured sample is kept with the tests. Until then, the report keeps
  listing attachments as "move by hand", as today.
- The generic importers (`docs/import.md`) stay without attachments.

### 6.2 Prisma

```prisma
enum AttachmentState { uploading ready deleted }
enum AttachmentStorage { db s3 }

/// A file on a record (docs/design/2026-10-12-attachments.md). Everything about the file is ciphertext:
/// encMeta (name, type, size, hash) and wrappedFileKey are v1. envelopes under the record key; the chunks are
/// AES-GCM under the file key. The server knows sizes, counts, who and when.
model Attachment {
  id             String            @id @db.Uuid
  recordId       String            @db.Uuid
  record         Record            @relation(fields: [recordId], references: [id], onDelete: Cascade)
  createdBy      String            @db.Uuid
  state          AttachmentState   @default(uploading)
  storage        AttachmentStorage @default(db)
  /// v1. under the record key, AAD attachment-meta:<recordId>:<id>.
  encMeta        String
  /// v1. under the record key, AAD attachment-key:<recordId>:<id>.
  wrappedFileKey String
  /// 8 random bytes (base64url); the chunk nonce is nonceBase || BE32(index).
  nonceBase      String
  chunkSize      Int
  chunkCount     Int
  /// Ciphertext bytes in total (declared at create, verified at complete). Int is enough: files are far below 2 GiB.
  size           Int
  createdAt      DateTime          @default(now())
  readyAt        DateTime?
  deletedAt      DateTime?
  chunks         AttachmentChunk[]
  links          ShareLinkAttachment[]

  @@index([recordId])
  @@index([state, createdAt])
  @@index([createdBy, createdAt])
}

/// One ciphertext chunk (db storage). The migration sets STORAGE EXTERNAL on data (no TOAST compression attempt).
model AttachmentChunk {
  attachmentId String     @db.Uuid
  attachment   Attachment @relation(fields: [attachmentId], references: [id], onDelete: Cascade)
  index        Int
  length       Int
  /// SHA-256 (hex) of data: makes PUT idempotent and detects bit rot.
  sha256       String
  data         Bytes

  @@id([attachmentId, index])
}

/// A file a one-time link carries (its key is inside the link's encrypted payload).
model ShareLinkAttachment {
  linkId       String     @db.Uuid
  link         ShareLink  @relation(fields: [linkId], references: [id], onDelete: Cascade)
  attachmentId String     @db.Uuid
  attachment   Attachment @relation(fields: [attachmentId], references: [id], onDelete: Cascade)

  @@id([linkId, attachmentId])
  @@index([attachmentId])
}

/// S3 objects to delete after a purge or cascade (db storage needs none: chunks cascade).
model AttachmentTombstone {
  attachmentId String   @id @db.Uuid
  storage      AttachmentStorage
  chunkCount   Int
  createdAt    DateTime @default(now())
}
```

`Record` gains `attachments Attachment[]`; `ShareLink` gains `attachments ShareLinkAttachment[]`; `BackupRun` gains
`attachmentBytes BigInt?`. Migration `2026102x000000_attachments`: the three tables, the enum types, the FK cascades,
the indexes and `ALTER TABLE "AttachmentChunk" ALTER COLUMN "data" SET STORAGE EXTERNAL`. No database trigger
writes tombstones: the purge and remove routes write them in their own transaction for `storage = 's3'` rows, and the
sweep handles the rest (cascades from org or account deletion can leave S3 orphans, which a daily pass of the sweep
finds by listing the bucket prefix against `Attachment` ids).

Quota queries (`lib/attachments/quota.ts`):

```sql
-- org usage
SELECT COALESCE(SUM(a.size), 0) FROM "Attachment" a JOIN "Record" r ON r.id = a."recordId" JOIN "Folder" f ON f.id = r."folderId"
WHERE a.state IN ('uploading','ready') AND f.kind = 'team' AND f."orgId" = $1;
-- person usage (private records)
SELECT COALESCE(SUM(a.size), 0) FROM "Attachment" a JOIN "Record" r ON r.id = a."recordId" LEFT JOIN "Folder" f ON f.id = r."folderId"
WHERE a.state IN ('uploading','ready') AND r."ownerId" = $1 AND (f.id IS NULL OR f.kind = 'private');
```

restart on reload), `downloader.ts` (chunks ×3 → decrypt → hash → save or preview), `AttachmentList.tsx`,

- **Record panel** (`RecordPanel.tsx`): a **Files** section under the fields, for every record type: each row shows

- **Drag & drop** on the open panel or editor (whole panel is the drop target with an overlay "Drop to attach to
  <title>"); `view`/`use` holders get "You can't add files here". Multiple files at once; each is its own upload.
- **Progress**: per file, a bar with MB and a Cancel; a "Retry" on failure keeps the already accepted chunks (same

- **Public link page** (`PublicLinkPage.tsx`): a Files list with Download only.
- **Offline**: files listed with "Available online", buttons disabled.
- **Lock**: locking the vault aborts in-flight uploads and downloads and zeroes file keys with the other keys
  (`session.tsx`'s lock path).
- Phone layout: the Files section and the drop zone work with the sheet layout; the file picker is the native one.

### 6.4 Previews and CSP

| Format (from encrypted `mime`, checked against magic bytes after decryption) | Sink | Notes |
|---|---|---|
| `image/png`, `image/jpeg`, `image/gif`, `image/webp` | `<img src=blob:>` | Allowed by today's `img-src 'self' data: blob:`. Never `image/svg+xml` (scriptable). |
| `application/pdf` | pdf.js (`pdfjs-dist`, Apache-2.0) rendering to `<canvas>`, worker from `'self'`, `isEvalSupported: false`, `enableScripting: false`, `enableXfa: false` | Not the browser's native viewer: Chrome's viewer is blocked in sandboxed iframes and a non-sandboxed `<iframe src=blob:>` would need `frame-src blob:` and would run PDF JavaScript in some viewers. pdf.js in the page runs under the app's CSP (`script-src 'self' 'wasm-unsafe-eval'`, no eval). Phase 5. |
| `text/plain` (≤ 1 MiB) | `textContent` into a `<pre>` | Never `innerHTML`. |
| anything else (HTML, SVG, XML, Office, archives, executables…) | download only | |

The magic-bytes check means a file whose metadata says `image/png` but whose bytes aren't PNG isn't previewed. CSP
needs **no change** for phase 1–4 (images use `blob:` under `img-src`; pdf.js adds a worker under `worker-src 'self'`
and canvases). `object-src 'none'` and `frame-ancestors 'none'` stay. Blob URLs are revoked as soon as the image has
loaded or the sheet closes.

### 6.5 Service worker

`apps/web/pwa/sw.js` already answers "skip" for everything under `/api/`, so chunk requests are never intercepted or
cached. `sw.test.ts` gets cases for `/api/v1/records/<id>/attachments/<fid>/chunks/0` and the public link chunk
path (both "skip"), so a future rule for static files can't catch them. API responses already carry
`cache-control: no-store`, and chunk responses add `content-disposition: attachment`, so the browser's HTTP cache and
"open in new tab" never apply.

## 7. Security analysis

| Threat | Analysis | Mitigation |
|---|---|---|
| **Malicious server swaps chunks** between files or positions | Each chunk's AAD binds file id, index and total; the file key is per file. Decryption fails (`decrypt_failed`), the client shows "File is damaged" and keeps nothing. | §2.2 AAD; whole-file SHA-256 as a second check. |
| **Truncation** (serve fewer chunks, or a shorter last chunk) | `chunkCount` is in the encrypted metadata and in every chunk's AAD; the client demands exactly that many chunks and the plaintext length must equal `meta.size`; a cut-off last chunk fails its tag. | §2.2; `complete` on the server verifies lengths too (defence in depth, not security-relevant). |
| **Replay / rollback** of an older chunk | Chunks are immutable after acceptance; the server never has two versions of a chunk under the same nonce (idempotent PUT accepts only identical bytes). | §4.2 hash check; client never re-encrypts under the same key after a reload. |
| **Nonce reuse** by a buggy client | Key and `nonceBase` are fresh per upload attempt; retries resend kept ciphertext; a new attempt is a new file id and key. | §2.2; unit test that two attempts of the same file never share a nonce+key. |
| **Key misuse** (file key presented for another record, wrapped key moved) | The wrap's AAD binds `recordId` and `fileId`; metadata AAD likewise. A wrapped key copied to another row doesn't open. | §2.1. |
| **Server re-attaches a file to another record** | Same AAD; and a client only trusts attachment rows that arrive under the record whose key opens them. | §2.1. |
| **Server plants a file on a shared record** | It can't: it has no record key to wrap a file key or encrypt metadata. A planted row shows "Can't open this file". | (Same trust limits as planted records in `docs/sharing.md`.) |
| **XSS via previews** | The client never navigates to or frames attachment content and never uses `innerHTML`. Images go to `<img>`, PDFs to canvas through pdf.js with scripting off, text to `textContent`. Download blobs are `application/octet-stream`, so a browser can't render an HTML attachment under the vault's origin even if someone opens the blob URL. SVG is never previewed. | §6.4, §7.5. |
| **Malware in attachments** | Can't be scanned server-side. The uploader's identity is in the event log and on every row; executables show a warning badge on download ("<name> is an executable file added by Ana; only open it if you expected it"); nothing auto-opens. Organisations that need scanning can turn previews off or attachments off by policy. | §1, §5.5, §6.3. |
| **Zip bombs** | The app never decompresses attachments. The Keeper import inflates its own zip entry by entry with a declared-size cap and an inflate budget. | §5.4, §7.6. |
| **Quota abuse** (filling the org's storage, DoS on backups) | Only `edit`+ can upload; reservations at create under a row lock; daily per-person cap; abandoned uploads swept in 24 h; per-user rate limits; the Risk dashboard alerts over 90 %; every refusal is logged with the actor. | §3.5, §4.7. |
| **Cross-org leakage** | Every route goes through `accessFor` with the active org: a record in another org's team folder is `404`, a share counts only where it was made, private records need the owner. Attachments add no path of their own. Quota accounting keys on `recordOrgOf`. | §4, test matrix §7.7. |
| **`use` holders downloading** | Server refuses chunk requests for `use`. Metadata (names) is readable with the record key, accepted. | §4.6. |
| **Revoked person keeps downloading** | Access rows go at once; chunk requests fail from then on. Already fetched ciphertext stays decryptable with the key they held (same as records). | §4.5. |
| **One-time link recipient** | Holds the real file key and a 30-minute download token; after that only the key. Revocation is immediate. Files are opt-in per link, capped, logged. Including a file in a link is as serious as including the password. | §5.1. |
| **Database thief / backup thief** | Chunks are AES-GCM ciphertext under keys that only exist wrapped under record keys; backups are age-encrypted on top. Nothing usable. | — |
| **Timing / size leakage** | The server knows sizes to within 16 B × chunks and which files are downloaded when. Accepted; stated in §2.6 and the help page. | — |
| **Memory on the client** | One chunk in flight ×3 for uploads; downloads stream to disk where the API exists, else up to the file limit in memory. | §4.4. |

### 7.5 Browser rules the client must follow (checked by tests)

1. Never `window.open`, `location =`, `<iframe>`, `<object>` or `<embed>` an attachment blob.
2. Download blobs are typed `application/octet-stream`; the filename goes through `safeFilename`.
3. Preview only after a magic-bytes check against the allowlist; `image/svg+xml` is never an image here.
4. `URL.revokeObjectURL` right after load / on close.
5. Decrypted bytes live in the preview or download path only; nothing decrypted is written to IndexedDB,
   `localStorage` or the Cache API.

### 7.6 Keeper zip guard

Per entry: skip when `uncompressedSize > ATTACHMENT_MAX_FILE_MB`; inflate through a counting stream that aborts when
the output exceeds the declared size; total inflated bytes per import ≤ the org's free quota; at most 25 entries per
record; entry names are not used for anything but the record mapping (file names come from the JSON).

### 7.7 Test plan

**Crypto (`packages/crypto/test/attachments.test.ts`)**
- Round trip: 0 B, 1 B, exactly 1 chunk, 1 chunk + 1 B, 3 chunks; metadata round trip.
- Negative: reorder two chunks → fails; drop the last chunk / lie about `chunkCount` → fails; swap a chunk from
  another file (same index) → fails; wrong record id or file id in the wrap AAD → fails; tampered byte → fails;
  metadata with inconsistent `size`/`chunkCount` → rejected; `safeFilename` cases (path separators, control
  characters, leading dots, 300-character names).
- Nonce uniqueness across two attempts of the same file; known-answer vector for one chunk (fixed key, base, index).

**API (`apps/api/test/attachments.test.ts`, Testcontainers Postgres; `attachments-s3.test.ts` against the MinIO
container the backup tests use)**
- Permission matrix of §4.6 for owner, edit, view, use, none, and for a direct share from another org (404), a record
  in another org's team folder (404), a confined session (private lock).
- Create: limits (file, per record count and bytes, org, user, instance, daily), policy off, trash, bad `size`
  arithmetic, reused id; concurrent creates against one quota (only one gets through).
- Chunks: wrong length, out-of-range index, JSON body (415), over body limit (413), idempotent re-send, mismatch
  (409), another editor sending to my upload (403), upload after share downgrade (403).
- Complete: missing chunk (409 with the list), success sets `ready`, touches `updatedAt`, leaves `revision`, logs.
- Download: order and bytes identical; `use` 403; trashed 409; `uploading` 404; logging deduplication.
- Remove: chunks gone, usage down, live link including it revoked; cancel of an upload.
- GC: abandoned upload swept after 24 h; purge removes chunks (db) and writes tombstones (s3) that the sweep clears.
- Move: into a team folder over quota → 409 and nothing changed; re-charge on success.
- Links: `attachmentIds` validation, token issue on open, chunk with token, token after expiry, revoked link, revoked
  creator right, trashed record, policy `links.allowAttachments` off.
- Sync: `attachments` present with the right fields and only `ready` rows; nothing for records I can't open.
- Backup: dump includes chunks (db), excludes chunk data (s3), `attachmentBytes` recorded.
- Rate limits per user, not per IP.

**Web (Vitest)**
- Uploader: plan, 3-way parallelism, retry keeps ciphertext, cancel sends DELETE, reload leaves no resume state,
  over-limit refused before any request, queue for a new record flushes after save.
- Downloader: ordering, hash mismatch → error and no blob, octet-stream blob type, filename.
- Preview sinks: allowlist, magic-byte mismatch → download only, SVG never previewed, object URLs revoked.
- `sw.test.ts`: chunk URLs are "skip".
- Panel and editor: Files section per permission, drop zone states, offline listing.

**End to end (Playwright)**
- Owner attaches a 5 MiB file and a PNG, previews the PNG, downloads the file (checksum equal); shares the record
  with a second user with Can view → they download; downgrade to Use only → the list shows locks and the chunk request
  is 403; remove the share → 404.
- Team folder: a member with Can edit attaches; the folder owner removes it; the member sees it gone after sync.
- One-time link with a file: open, download, link revoked → chunk 410/404.
- Trash → downloads refused; restore → back; purge → chunks gone (query the db in the test).
- Offline copy: the file is listed as online-only.
- Phone layout: attach from the sheet, progress visible.

## 9. Open questions

- **Q1.** Should `use` holders see file names at all? They see the record's title and username today, and hiding
  names would need metadata under a second key. Recommendation: visible, download refused (§4.6).
- **Q2.** Per-attachment trash (restore a removed file within 30 days)? Costs quota while in trash and a second
  state machine. Recommendation: not in 1.6; the record's trash covers the common case.
- **Q3.** Should a file in a one-time link get its own fresh key (re-encrypted copy, so the vault's file key never
  leaves the vault)? Doubles storage for the link's lifetime and the creator's upload time. Recommendation: no;
  opt-in plus logging plus a short token is proportionate, and the record's password is in the same link anyway.
- **Q4.** Chunk size 1 MiB versus raising the body limit to 5 MB and using 4 MiB chunks. Recommendation: 1 MiB now
  (zero proxy changes); revisit if request count becomes the bottleneck.
- **Q5.** Image thumbnails in the Files list without a click: would download and decrypt every image on panel open.
  Recommendation: click to preview; maybe auto-preview images under 512 KiB later.
