## Unreleased

Upgrading: migration `20261024000000_customer_orgs` runs on start (two nullable columns on `Organization` and an index). No `.env` change.

- **Organisations for customers** (`docs/provisioning.md`): instance admins create an organisation for a customer in one step, in **Server → Customer organisations**, with its name and the owner's email address. The organisation starts with no members and an owner invitation, so the operator never joins it: a new person signs up through the link (HOSTED_MODE: emailed only, with the sign-up code), someone with an account accepts from the organisation menu, and either way they become its only owner. Accepting counts toward the invitee's `MAX_OWNED_ORGS` (`409 org_limit`); creating isn't limited by `ALLOW_ORG_CREATION` or `MAX_OWNED_ORGS`. The owner's browser makes their membership keys on first unlock, as in any organisation. The list shows only the name, date, owner's address and whether the invitation is pending, expired or accepted, with **Resend invite** and **Cancel** (which deletes the never-joined organisation). This replaces creating the organisation yourself, inviting the customer as an admin, transferring ownership and leaving. API: `GET`/`POST /admin/instance/orgs`, `POST /admin/instance/orgs/:orgId/resend`, `DELETE /admin/instance/orgs/:orgId`. Events `org.create` (`for: "customer"`) and `admin.invite` in the new organisation's log; `instance.customer_org_create`, `instance.customer_org_resend` and `instance.customer_org_cancel` at instance level. A customer organisation's invite link stays an owner invitation when it meets an existing account; other owner links (bootstrap) still become admin invitations.
- Fix: nobody could reset an organisation owner's authenticator, although `docs/recovery.md` said instance admins could. Instance admins now reset anyone's by email address in **Server → Accounts → Reset someone's authenticator** (with a confirmation step), owners included and without being a member of their organisations: `POST /admin/instance/users/reset-2fa` (`{ email }`, 10 a minute). It does what **Reset 2FA** on People does (back to authenticator setup, signed out everywhere, emailed) and logs `instance.reset_2fa` at instance level. It refuses the instance admin's own account (`400 self`). For that case, and for self-hosted servers, the operator's command `node dist/src/scripts/reset-2fa.js --email …` does the same.
- Fix: an admin could switch off the owner's "Require SSO" or email domain auto-join by removing the last verified SSO domain. While either is on, only the owner can remove that domain (`403 owner_only_last_domain`, and the app says why); admins can still remove other domains, and the last one when neither is on.

## 1.6.2 — 2026-10-13

Upgrading: no migration and no `.env` change. The image no longer has a shell, so anything you run inside the container must be a `node …` command: the documented `docker compose exec clane-vault node dist/src/scripts/…` commands work as before, but `sh`, `bash`, `rm`, `cat`, `curl` and `wget` are gone. A health check of your own must use the exec form, e.g. `test: ["CMD", "node", "dist/src/scripts/healthcheck.js"]` (the image now has this one built in, so you can drop yours); `CMD-SHELL` checks fail. Restore now reads the key from standard input (`docker compose exec -T clane-vault node dist/src/scripts/restore.js … --identity - < backup-key.txt`) instead of copying it into the container and deleting it with `rm`. The container still runs as uid 1000, so mounted backup folders keep working.

- Security hardening of the image (Trivy: 84 HIGH/CRITICAL findings in 1.6.1, 1 in this one, which can't be reached: see below). The runtime is now distroless Node.js 22 on Debian 13 (`gcr.io/distroless/nodejs22-debian13:nonroot`, pinned by digest): no shell, package manager or npm, and none of Debian's util-linux, perl, ncurses tools, systemd libraries or gzip. `pg_dump`, `pg_restore` and `psql` 17 (PGDG) are copied in with only the libraries they need, so built-in backups and the restore CLI work as before. Only the API's production dependencies ship (no TypeScript compiler, test tools or the web app's build tools); app files are owned by root and read-only for the app. The image is about 155 MB to download instead of 347 MB (655 MB unpacked instead of 1.6 GB). The one finding left is CVE-2025-69720, reported against Debian's ncurses packages: the bug is in the `infocmp` program, which isn't in the image (only `libtinfo`, loaded by `psql`, which the restore runs without a terminal).
- Startup without a shell: `node dist/src/scripts/start.js` runs `prisma migrate deploy`, stops with its exit code if it fails, then starts the server. `docker stop` now stops the server cleanly within a second (in-flight requests finish) instead of waiting 10 seconds to kill it. Built-in Docker `HEALTHCHECK` (`dist/src/scripts/healthcheck.js`, which follows `PORT` and `BASE_PATH`); `deploy/docker-compose.yml` uses it.
- Dependencies: nodemailer 8.0.11 → 10.1.0 (SMTP; CVE-2026-82659, GHSA-2x7j-588g-ccc2, GHSA-v53p-9fqp-m79j; it ships its own types now). deepmerge-ts 7.1.5 → 8.0.2 through an npm override (CVE-2026-40345; pulled in by Prisma 6.19.3, the latest 6.x). `prisma` moves to the API's dependencies, as the container runs its migrations. Prisma's `binaryTargets` now name the image's engine (`debian-openssl-3.0.x`).
- Restore CLI: `--identity -` reads the age identity from standard input. The README and **Admin → Backups → Restore a backup** show that form.
- Risk dashboard: the password health benchmark said "All 1 reporting member are above 60…"; it now reads "The 1 reporting member is above 60…" for one member and "All 3 reporting members are above 60…" for several.

- **File attachments** (`docs/attachments.md`), end-to-end encrypted, on every record type, private or shared: **Attach file** in the record's Files section, drag & drop onto the open record or the editor (new records queue files and upload them right after the first save), several files at once, per-file progress with Cancel and Retry, a paperclip count in the list. **Preview** for PNG, JPEG, GIF, WebP (after checking the bytes really are that format; never SVG), PDF (pdf.js on a canvas, no scripts, under the app's existing CSP) and plain text; everything else is download-only, saved as `application/octet-stream` (streamed to disk in Chrome and Edge). Programs warn before they download. Each file has its own random key, wrapped under the record key; 1 MiB chunks are AES-256-GCM with nonce = 8 random bytes ‖ chunk index and the file id, index and chunk count bound in, and the whole file's SHA-256 is checked after download, so chunks can't be swapped, reordered, truncated or replayed. The server stores ciphertext and learns sizes, counts, who and when; never names, types or content. Access follows the record: sharing shares the files with nothing re-encrypted, removing access stops downloads at once, and **Use only** can see file names but can't download (enforced by the server, `403 use_only`). Trash keeps files (listed, not openable); deleting forever removes them. Limits and quotas (`ATTACHMENT_*`): 100 MB a file, 25 files and 250 MB per record, 2 GB per organisation, 512 MB per person for private records, 10 GB per server, 2 GB of uploads per person per day, checked before anything is sent and reserved under locks on the server. Organisation policies: **File attachments** (off: no new uploads), **Largest file**, **File previews**, and **Allow files in links**. One-time links can carry files, opt-in per file (at most 25 files, 100 MB), with a 30-minute download token after opening; revoking the link, removing the file or trashing the record stops it. The offline copy lists files as "Available online" (content is never stored on the device); the browser extension ignores them. Events `attachment.add`, `attachment.remove`, `attachment.download`, `attachment.upload_abandoned`, `attachment.quota_exceeded`, `link.attachment_download`, shown in the record's Activity. Risk dashboard: **File storage** tile (by member, CSV), a "File storage under 90 %" benchmark and alerts for refused uploads, link downloads and downloads from widely shared records. Admin → Organisation settings → **Storage** (usage, largest records, limits) and Server → **Storage** (backend, per organisation, clean-up with **Run now**, backup note; a banner past 80 % of the server quota). Abandoned uploads (24 h), removed files and purged records are cleaned up by the sweep.
- Storage: files live in Postgres by default (one container, one backup; chunk data stored out of line without compression), or in an S3-compatible bucket with `ATTACHMENT_STORAGE=s3` (Supabase Storage, R2, MinIO, AWS; a bucket and key of their own). Every byte goes through the API (no pre-signed URLs). `node dist/src/scripts/attachments-move.js --to s3|db` moves existing files, resumably. Backups: `pg_dump --compress=1`, and with S3 storage (once no file is left in the database) the chunk data is left out of the dump: back the bucket up yourself. Backup runs record the attachment bytes they cover.

Database migration `20261021000000_attachments` (tables `Attachment`, `AttachmentChunk`, `ShareLinkAttachment`, `AttachmentTombstone`; `BackupRun.attachmentBytes`).

Admins can now rename the organisation too (previously only the owner). Events: `org.logo_set`, `org.logo_remove`, and `org.rename` now records the old and new name.

This overrides `VITE_PRODUCT_NAME` / `PRODUCT_NAME`. The public `GET /api/v1/brand` is loaded at boot, and the app falls back to the build's names if it fails. Emails and the authenticator issuer use the stored name. The CSP's `img-src` adds `blob:`. Database migration `20261016000000_branding_logos` (`OrgLogo`, `InstanceBrand`).
- Installable app (PWA, `docs/install-app.md`): web manifest from the product branding, a service worker (`/sw.js`, served `no-cache`) that caches only the app shell and static files and never `/api/`; CSP adds `worker-src 'self'; manifest-src 'self'`.
- Offline read-only copy (Settings → This device, on by default): the account's wrapped key material and each org's last sync response, ciphertext as received, in IndexedDB. Without the server the unlock screen opens it with the master password, read-only with an "Offline — read only" banner; the app returns to normal when the server is back. Wiped on sign-out (the server session ends at the next start if signed out offline), on a refused session, on account switch and when switched off; organisations whose policy forbids offline copies are not stored.
- Phone layout (375 px and up): top bar with menu, lock and + New, the sidebar in a drawer, full-screen sheets and dialogs, 40 px touch targets on touch screens, list → detail with Back.
- Importers (`docs/import.md`): Zoho Vault CSV, LastPass CSV, 1Password 1PUX and CSV, Dashlane CSV, and any other CSV with a column-matching step and preview.
- Browser extension for Chrome, Edge and Firefox (`apps/extension`, `docs/extension.md`): sign in with master password and authenticator code against a server chosen on first run, items for the current site first, search, copy username / password / one-time code (clipboard cleared after 30 s), click-to-fill only into the top frame with registrable-domain matching (mismatch and plain-http pages need an explicit confirmation), "Use only" items fill but never copy, password generator, organisation switcher, auto-lock (15 min by default, org `autoLockMinutes` shortens it, screen lock locks), and opt-in save/update offers that store new logins in the private vault. Keys stay in memory and `storage.session` only.
- API: `POST /auth/login` takes `client: "extension"` and then returns the refresh token in the body instead of the cookie; `/auth/refresh` and `/auth/logout` accept it in the body when there is no cookie (only for those sessions), with the same rotation, compare-and-swap, grace window and reuse detection. These sessions are labelled "Browser extension".
- Web: Settings shows a "Browser extension" card with the server address to connect to.
- Groups per organisation (`docs/groups.md`). Admins manage groups on the People page. Folder owners share team folders with a group at edit, view or use. Group members get the folder key once an owner or editor approves them (see below), including people who join later. Effective access is the highest of the direct and group grants. Removing a person or a group ends only the access that came through it. Every change is in the event log.
- Organisation policies (`docs/policies.md`), edited in Settings → Organisation:
  - auto-lock minutes;
  - master password minimum length and strength (enforced at sign-up and before joining);
  - one-time links: on or off, maximum expiry, password required (enforced by the server; switching links off revokes the org's live links);
  - offline copies, browser extension and breach check flags, which clients read with the org list;
  - an IPv4/IPv6 IP allowlist for org-scoped requests, with a logged owner break-glass and lock-out protection.
- Password health page (`docs/password-health.md`): weak, reused, old (new optional `passwordChangedAt` in the record body) and, opt-in, breached passwords via the Have I Been Pwned k-anonymity range API (`connect-src` now allows `https://api.pwnedpasswords.com`). It shows a score and filterable lists. Only counts and the score are posted; admins see them per member.
- Event log page for admins: filter by person, action and date range, and export to CSV (`GET /admin/events/export.csv`, streamed, protected against spreadsheet formulas, logged).
- Per-organisation key pairs (`docs/design/2026-10-08-per-org-keypairs.md`): each membership has its own key pair. Team folder keys and direct shares made in an organisation are sealed to it, and the client moves older copies over on unlock (online, resumable).
- Admin recovery works for people in several organisations and is scoped to one organisation. An admin's link restores what the member holds in that organisation, never their private items or other organisations. The reset gives the member new account keys and archives the old ones. The old recovery kit or old master password restores the rest later (Settings → Security), and another organisation's link restores that organisation without a reset. The recovered key is replaced on the next unlock. Members see which admins hold their escrow. Joining another organisation no longer turns admin recovery off.
- Group access is never sealed automatically: owners and editors approve or decline each waiting group member, seeing who it is, the group and who added them, and the key fingerprint (with a warning when it changed). New endpoint `POST /folders/:id/group-access/decline`.
- Folder owners and editors can give a member their folder key again after an account reset ("Needs access again"), and record owners can share again.
- Security review: renaming a private folder no longer logs the active organisation, and records in an organisation's team folder can't be moved out to private (`409 org_record`), so they stay under its link policy.
- Database migration `20261014000000_membership_keys`: membership keys, membership escrows, account key archive, `sealedTo` on folder memberships and shares, group-access declines. **It deletes the old whole-account escrows and ends open admin-recovery requests.** Members escrow again on their next unlock.
- Security review of per-organisation key pairs: the key archive left by a scoped reset opens only with the old master password or old recovery kit checked server-side (not a session and 2FA code alone, which would allow offline guessing of the old password); admin recovery links no longer return the wrapped user key (`POST /auth/recovery/restore-membership/material` gives it after the current password checks out); `PUT /membership-key/rows` takes `to` and refuses a batch sealed to a key another device just rotated away (`409 stale_key`), so no access is lost; the creator's own copy of a new team folder key goes only to a membership key the device can open; key pins cover account keys, so a dropped membership key warns; escrows of retiring keys are not released. Database migration `20261015000000_key_archive_auth`.
- Database migration `20261013000000_groups_policies_health`: adds groups, folder group grants, `FolderMember.directPermission` (backfilled), organisation policies, health reports and an `Event(orgId, at)` index.

## 1.0.0

First stable release; upgrade straight from 0.5.3 (database migrations run automatically on start; take a backup first).
**0.5.0, 0.5.1 and 0.5.2 must not be used** (recovery hardening and the admin-recovery link window were fixed in
0.5.1–0.5.3); 0.6.0 was never released and is part of this version.

Summary since 0.5.3:

- **Multiple organisations** on one server: global accounts, org-scoped roles, invites, team folders, shares, links,
  admin recovery and events; an org switcher; `X-Org-Id` checked against an active membership on every request.
- **Hosted mode** (`HOSTED_MODE`): invite links only by email, sign-up codes, invite caps and cooldowns, name cleaning,
  instance admins as an account flag, admin recovery only for single-org accounts.
- **Email settings in the app**: server-wide and per-organisation, Resend or SMTP, test email, secrets encrypted at rest;
  every security notice uses the server's settings.
- **Single sign-on** (OpenID Connect) per organisation with verified domains, Require SSO, trusted IdP MFA and
  just-in-time joining, keeping zero-knowledge (the master password still unlocks the vault).
- **Hardening** from two multi-org reviews and the email/SSO security review (details below).

Details:

- Email settings in the app (`docs/email.md`): instance admins set the server's email under Settings → Email, and organisation admins can give their organisation its own (used for its invites and notices). Providers: Resend (API key) or any SMTP server (host, port, STARTTLS / TLS / none, username, password). "Send test email" sends to your own address and shows a short, credential-free reason when it fails; 10-second timeouts. API keys and passwords are encrypted at rest (AES-256-GCM, key derived from `SERVER_SECRET`, bound to the settings row), never returned (only "set" and an API key's last four characters) and only replaced when typed. Changes and tests are in the event log (`email.settings_updated`, `email.settings_removed`, `email.test`). `RESEND_API_KEY` / `EMAIL_FROM` remain the fallback. `HOSTED_MODE` refuses organisation SMTP hosts on private addresses.
- Single sign-on with OpenID Connect per organisation (`docs/sso.md`, Settings → Single sign-on): issuer discovery, client ID and secret (encrypted like email secrets, never returned), "Test connection" (discovery, PKCE support, client credentials), email domains verified by a DNS TXT record `clane-vault-verify=<token>`, and options "Require SSO for members", "Trust the identity provider's MFA" and "Auto-join verified domain users". Authorization Code + PKCE + state + nonce, id_token checks (issuer, audience, expiry, nonce), a verified email required (Entra: `xms_edov`), and the identity (issuer + subject) linked after the first sign-in so a changed email at the provider can't take over another account. Zero-knowledge is kept: after SSO the master password is still needed (the server checks its auth key as always); the authenticator code is skipped only when the organisation trusts its provider's MFA and the person is a verified-domain member. New people in a verified domain sign up through SSO (auto-join or an open invite) without an emailed code. "Require SSO": verified-domain members reach the organisation only from a session its SSO established (`403 sso_required`, the app offers "Sign in with <org> SSO"); the owner is exempt. Sign-in page: "Continue with <org> SSO" for verified domains and "Sign in with SSO" with an organisation ID. Single-use, browser-bound requests and proofs, open-redirect-safe `returnTo`, rate limits, redacted callback URLs and audit events (`sso.*`). New setting `SSO_ALLOW_HTTP_ISSUER` (development only).
- Sessions that skipped the authenticator code (trusted IdP MFA) don't see the person's own private folders and records until a TOTP step-up: sync leaves them out (the app shows a locked "Private items" row) and private record, folder and link routes answer `403 totp_step_up_required`.
- Security review of email and SSO: trusted-IdP-MFA sign-ins skip the authenticator code only for single-organisation, non-JIT, verified-domain members (and an MFA `amr` when sent), and the session stays confined to that organisation until a TOTP step-up (`403 totp_step_up_required`, `POST /auth/totp/step-up`); "Test connection" never sends the stored client secret to another issuer or client; a stored SMTP password is dropped when the host, port or security changes, and `HOSTED_MODE` refuses SMTP passwords without encryption and org SMTP ports other than 25/465/587/2525; every security notice uses the server's email settings; id_token signatures are checked against the JWKS; `SSO_ALLOW_HTTP_ISSUER` refuses to start with `HOSTED_MODE` or in production; renamed IdP addresses sign in with the account's own KDF salt. Also: DNS-rebinding-safe connections in hosted mode, generic error details, one organisation per verified domain, no public mail providers as SSO domains, TXT re-checks (daily) before JIT joins and sign-ups, owner-only SSO trust settings with emails to owners and admins, `sso.bypass_owner` events, use-time checks of auto-join and trust, atomic proof attempts, identity linking only after a new authenticator is set up, `409 account_exists`, a per-organisation limit on SSO starts, and cleaned IdP error text.
- Database migrations: `EmailSettings`; `OrgSso`, `SsoDomain`, `SsoIdentity`, `SsoLogin`, `SsoProof`, `Session.ssoOrgIds` and `Session.totpSkippedForOrg`, `SsoDomain.checkedAt`, `SsoProof.idpMfa` (applied automatically on start).

Multi-organisation work (developed as 0.6.0, never released):

- Multiple organisations on one server (`docs/design/2026-10-07-multi-org-design.md`). Accounts stay global (one master password, keys, 2FA and recovery kit); roles, admin rights, disablement, invites, team folders, direct shares, links on organisation records, admin-recovery policy, escrows, recovery requests and events belong to one organisation. Private folders and records belong to the user and show in every organisation.
- Every organisation-scoped API call carries `X-Org-Id`, checked against an active membership on each request (`403 org_forbidden` / `org_required`). Sync, the people picker, sharing and every admin route only see the active organisation.
- Org switcher at the top of the sidebar (organisations with your role, invitations with Accept/Decline, Create organisation, Organisation settings); the last organisation is remembered per user on each device and caches never cross organisations.
- Inviting someone who already has an account creates an invitation they accept in the app. Admins can remove people from the organisation (offboarding), change admin/member roles, and owners can rename, transfer ownership, delete (team folders go to the trash) or members can leave.
- Disabling a member now applies to that organisation only. Resetting 2FA (which changes the whole account) needs an instance admin or an admin of every organisation the member belongs to.
- Backups are instance-level: only instance admins see them. Instance admin is an account flag (the bootstrap account, the main organisation's owner after the migration, or `scripts/instance-admin.js --email … --grant|--revoke`), never an email in configuration. `scripts/org-owner.js` sets an organisation's owner.
- Security review hardening: `HOSTED_MODE` (invite links only by email, sign-up needs an emailed 6-digit code); invites answer the same whatever the address (no account oracle) and show only the email until accepted; daily invite cap per org (`INVITES_PER_ORG_PER_DAY`, 50) and a 24-hour cooldown after a decline; organisation and display names are cleaned and may not contain links or addresses; admin recovery only applies to people in exactly one organisation (joining a second ends escrows and requests, with emails); record activity and links only show the active org's; owners' 2FA can only be reset by an instance admin; organisation deletion deletes its team folders; per-user cap on owned organisations (`MAX_OWNED_ORGS`, 5); the app pins each operation to the org it started in. Re-review: account row locks around every "exactly one org" decision and re-checks at escrow release, approval, link use and finish; atomic sign-up code attempts with a total cap per invite and a cap on codes sent; org deletion removes its events; instance admin is revoked when the account leaves the main organisation's admins; converted invitations keep the invite's date.
- New settings: `DEFAULT_ORG_NAME`, `ALLOW_ORG_CREATION` (default false), `HOSTED_MODE` (default false), `INVITES_PER_ORG_PER_DAY`, `MAX_OWNED_ORGS`.
- Database migrations: existing data moves into one main organisation; the longest-standing admin (or, without one, the longest-standing active member) becomes its owner and the instance admin (applied automatically on start).

## 0.5.3

- Admin recovery for a member whose 2FA was reset: the approving admin must have been an admin for at least `ADMIN_RECOVERY_APPROVER_MIN_AGE_DAYS` (default 7) before the reset (checked at escrow opening, approval, link use and finish; error `approver_too_new`), so one admin can't get around the two-person rule with a second admin account they invited. Admin accounts record when they became admin (existing admins: their creation date).
- Members are emailed when an admin resets their 2FA; all admins are emailed when a new admin account becomes active (event `admin.added`).
- Docs: exactly what the two-person rule guarantees, and the remaining risk (an honest reset plus one rogue long-standing approver).
- Database migration: `User.adminSince` (applied automatically on start).

## 0.5.2

- Admin recovery for a member whose 2FA was reset: the approved link now stays valid until 24 hours after the reset waiting period ends (`max(approval + 24 h, reset + ADMIN_RECOVERY_RESET_DELAY_HOURS + 24 h)`), so approving right after the reset no longer produces a link that expires before it can be used. Other links still expire 24 hours after approval.

## 0.5.1

**0.5.0 must not be deployed: recovery hardening.** Upgrade straight to 0.5.1.

- Admin recovery after a 2FA reset: the admin who reset a member's 2FA can't also approve their reset (in either order), and the link only lets the member set up a new authenticator after `ADMIN_RECOVERY_RESET_DELAY_HOURS` (default 24) since the reset. Approving for a member whose 2FA was reset now works (with a second admin). The member is emailed when an admin opens their escrow and when a reset is approved.
- Turning admin recovery on needs the admin's master password and a fresh 2FA code; every member is emailed, and each member must acknowledge a one-time in-app notice before their vault key is escrowed.
- 2FA codes are single-use per account (sign-in, 2FA setup, recovery, approvals, policy changes).
- Wrong 2FA codes on an admin recovery link count toward burning it (5 attempts); disabling an admin burns links they approved; escrow uploads replace existing ones; rate limits on escrow upload and approval.
- New optional settings: `ADMIN_RECOVERY_RESET_DELAY_HOURS`, `RATE_LIMIT_PER_MINUTE` (default 300).
- Database migration: 2FA step/reset and acknowledgement columns on `User` (applied automatically on start).
